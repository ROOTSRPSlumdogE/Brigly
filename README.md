# Brigly

The restaurant workspace in `demo.html` has been rebuilt around seven features:

- Team schedules: weekly roster, manager shift creation/editing/removal, overlap checks.
- Opening & closing lists: manager-maintained templates with completion recorded by person for each date and service.
- Specials: service-specific menu notes, prices, ingredient/allergy notes and availability.
- Stock: one stock list per team that drives both the 86 board and purchasing (replaces the separate 86 list and Supplies screens).
- Shift onboarding: lives on Today. Briefings are authored by managers or crew; per-person acknowledgments reset on revisions; shift notes are added, edited and archived in place.
- Reservations: guest notes, party size, table assignment, two-hour table conflict checks and arrival lifecycle.

## Run locally

Requires Node 20+; no npm dependencies.

```powershell
npm run check
npm run build
npm run preview
```

Open `http://127.0.0.1:8000/demo.html`. The marketing homepage remains in `index.html`.

## Implementation

`assets/js/workspace-state.js` holds the versioned model, validation and mutations. `assets/js/demo.js` renders the seven sections and handles forms. `assets/css/demo.css` provides responsive layouts using Brigly's local Plus Jakarta Sans font and brand palette.

The preview starts with sample data for The Copper Room, seeded for the current local date. Active configured team members are available in the sidebar identity selector, listed with their role title (Server, Bartender, Head chef…); the sidebar profile shows the role and home station. Data is stored under the `brigly-workspace-v2` localStorage key and upgraded in place as features expand; the original nine-module prototype's separate key is preserved but not imported. There is no backend, sign-in, cross-device synchronization, supplier integration or reservation integration. Role controls demonstrate workflows, not security boundaries. Browser storage failures are surfaced in the footer.

Schedules support same-day and overnight assignments. Lists share templates but isolate progress by date and service. Specials, notes, briefings, 86 items and reservations are service-specific; supply requests carry across services. Table bookings use a fixed two-hour window. Allergy notes must be verified with the kitchen.

`npm run check` verifies static references and script syntax, plus state tests for persistence, role controls, scheduling conflicts, shift isolation, briefing revisions, supply approvals and reservation conflicts/lifecycles. `npm run build` writes the static deployment bundle to `dist/`.

## Expanded Team Schedules

The scheduling domain lives in `assets/js/schedule-state.js`; the schedule UI is in `assets/js/schedule-ui.js`. Existing browser data is upgraded in place, preserving all seven modules. Sample hourly rates are seeded for the demo; managers can edit defaults per person or rates and unpaid breaks per shift.

Crew can switch among the sample teammates through **Preview as**, see their weekly shifts and overlapping coworkers, submit time-off requests, report sickness or lateness, request a two-way shift exchange, respond to swap invitations and enter daily tips. Managers see attendance alerts, a review queue, a roster with absence/late markers, individual or whole-team earnings and per-person rate/absence defaults.

Calculation rules:

- Roster hours = shift duration minus unpaid breaks. Expected working hours also remove reported lateness and absences.
- Time off changes estimates only when approved. Managers can choose paid/unpaid for each request, including correcting approved leave.
- Sickness updates expected coverage immediately, using the person's saved paid/unpaid default provisionally; manager review can override it. No medical details are required.
- Lateness updates expected minutes immediately. A manager can confirm or correct the minutes, including zero. Sickness takes precedence over lateness to avoid double deductions.
- Gross wages = (expected working hours + paid absence hours) × the saved shift rate, rounded to cents per shift. Reported daily tips are added to the total. Editing a tip entry replaces that person's total for that date.
- Daily, Monday–Sunday weekly, calendar-month and overall summaries use the selected date and include all services. Past values remain estimates, not verified worked time. There is no tax, overtime, deductions or payroll processing.
- Default rate changes affect new shifts only. Existing shifts retain their rates. Absence default changes affect new requests only.
- Swaps require the invited teammate's acceptance and then manager approval. Both assignments exchange atomically; each person retains their prior rate for the exchange. Conflicts, approved leave and attendance are rechecked. Editing a referenced shift invalidates a pending swap.
- Browser tabs on the same origin receive updates. An open form becomes stale if another tab changes the workspace and must be reopened before saving. This is still a local prototype; it does not send external notifications or synchronize between devices.

Verification covers state migration, paid/unpaid overrides, absence and lateness calculations, tip replacement, period aggregation, actor restrictions, teammate consent, swap approval/conflicts, stale swaps and default rates. Browser checks cover the crew/manager workflows, persistence, tab updates, stale forms and desktop/mobile layouts.

## Shared shift operations and manager reporting

`shift-operations-state.js` and `shift-operations-ui.js` connect the schedule with notes, menu availability, reservations, team configuration and reports.

- A shared shift is a **service date + service name**. Notes appear in each matching crew shift card and in Onboarding. Manager-authored notes are highlighted and sorted first; crew can edit/archive their own notes. Crew need an assignment on that service to post.
- The 86 list is now service-specific. Crew submissions are **Reported** (unconfirmed); managers approve or decline with feedback. Manager-created items start **Approved**. Managers can mark stock available again. Earlier global 86 data migrates to its saved date/service. Pending reports are available across dates in the manager's **86 review** tab.
- Shift briefings display reservation arrivals, parties, tables, guest notes and status; the linked reservation editor retains the selected date/service.
- **Team & schedule setup** supports adding/editing/archiving people, role titles, default stations and manager/crew access. Archiving preserves history and prevents new assignments. Role and station names can be added/renamed; only unused options can be removed.
- Services can be added, renamed or archived, with default start/end times and unpaid breaks. Renaming preserves linked notes, reservations, 86 items and checklist progress. Time changes apply to new assignments by default; managers may explicitly update assignments from a chosen date. Conflicts block the entire change. Individual assignments remain editable.
- Overnight shifts are supported. An end time before its start finishes the following day. Reports attribute the whole assignment to its service/start date. Overlap checks span midnight.
- Manager dashboards show **estimated labor cost**, using gross wages including paid absence, excluding crew tips. Crew dashboards retain **expected gross earnings** including their tips. Employer taxes/benefits, overtime, clocked actual hours and payroll finalization are not modeled.
- **Team reports** generates live statistics for a chosen person and date range: shifts, roster/expected hours, paid/unpaid absence hours, sickness/time-off counts, reported and confirmed late shifts, late minutes, pending reviews, wage expense, separate tips, note/86 contributions and per-shift records. “Not recorded” is distinct from on-time attendance. There are no inferred performance scores or automated employment recommendations.
- CSV downloads contain the same person/date scope and per-shift data, with formula-safe text cells. Reports are recalculated in the app; no emails, external HR integrations or scheduled background jobs are sent or created.

The preview identity selector now includes all active configured team members. Manager access is a simulated application role; this browser-local prototype still requires a backend and real authorization before shared production use.

### Default service checklists, custom checklists, and shift-specific task segregation

- **Default service checklists**: Managers can configure default templates tailored to each service (e.g. Lunch vs Dinner) so routines repeat automatically everyday without manual re-entry. In Checklists, managers can toggle between "This shift" and "Default service checklists" mode to view or edit templates for any service, add/edit/clear default tasks, or click "Save as service default" to promote a curated shift checklist into the service's permanent daily default.
- **Custom checklists**: Checklists are no longer restricted to Opening and Closing. Managers can create custom checklists for any occasion—such as "Event Setup", "Mid-shift Prep", or "Deep Clean"—both as permanent service defaults and as shift-specific routines. Custom checklists appear dynamically in station phase tabs and throughout Today and history views.
- **Shift-specific tasks**: One-off or ad-hoc tasks added outside the standard routine are flagged as shift-specific (`specific: true`). They are presented separately in their own panel with distinct orange badges and separate progress tracks in Checklists (`duties-ui.js`), and featured in a dedicated "Special & event tasks for this shift" card on Today (`shift-home.js`). Shift-specific tasks integrate cleanly into task notes, 86 reporting, completion attribution, and multi-day manager audit reports.

### Stock: the stock list, 86 board and purchasing in one place

The separate 86 board and Supplies screens are combined into **Stock** (sidebar, phone dock and service rail). Old `#eighty-six`, `#orders` and `#supply` links, saved views and notifications open the matching Stock section.

- **Stock list.** Managers keep one catalog of items. Each item has a category, vendor (or *Made in house*), the **teams** (stations) that may use it, order unit and pack size, unit cost, par level, storage area and an optional vendor SKU. Crew see only items for their teams: their home station plus any station they are rostered on for the selected service. A bartender can 86 or order limes but not halibut; kitchen crew can. Other teams' lists are view-only. Rows show live status: 86’d this service, below par, requested, on the order sheet, on order with its arrival date.
- **86 from the list.** The 86 action and every older entry point (Today, shift sheets) open a picker limited to the team's items. It offers quick reasons and an optional restock request in the same step. Crew 86s stay *Reported* until a manager approves them, as before. An item can't be 86’d twice for one service. Free-text 86s from checklist notes link to stock items when the name matches. On the 86 board, each card shows whether a restock is requested, on the order sheet, or arriving.
- **Ordering.** Crew tap **+** to build a request (cart) and send it with a note. Managers review requests: adjust quantities, approve, or decline with a reason. Manager additions skip review, and repeat additions merge into one line.
- **Order sheet (manager).** Approved lines are grouped **by vendor** (default, one purchase order per vendor), **by team** or **by category**. Vendor cards are sorted by the next order cut-off. Each shows delivery days, the cut-off and arrival date, an estimated total and progress toward the vendor minimum. **Copy order** gives formatted text or CSV for emailing the rep. **Place order** assigns a PO number and the expected delivery date.
- **Inventory counts (Count).** Crew count their own teams; managers can count any team. Each team has one open count sheet at a time. The sheet is grouped by storage area in walking order (walk-in, freezer, pastry, dry store, bar back, beer cooler, wine cellar, front of house, supply closet), shelf to sheet. Each row has a −/number/+ control and a *Last count* shortcut, Enter moves to the next item, and entries save as you go, so several teammates can count together or pick it up later. Finishing updates on-hand for counted items; skipped items keep their last count. It also records **usage** per item: last count + deliveries checked in − this count. A negative usage ("more than expected") points to a delivery that wasn't checked in, or a miscount. A result card then offers to request or order everything that came out below par. Teams are **due** after 7 days without a finished count. Due and in-progress counts appear on the Count tab badge, in Shift pulse and in the summary rail. Managers also see on-hand value (quantity × unit cost) per team. Count history opens each count with per-item usage. *Update count* in the item sheet stays for quick spot checks.
- **Count assignments.** Managers assign a count from Stock → Count (*Assign* on a team card or under *Scheduled counts*) or from Today. Each assignment has a team, a person or the whole team, a due date, an optional note and an optional weekly repeat. The counter sees it on **Today** in *Up next for you* from the day before (due date, note, progress) with *Start count* / *Continue*, which opens the count sheet directly. It also appears on their team card in Stock → Count, at the top of that team's list in Checklists, and Shift pulse reminds them the day before, on the day and once it's overdue. Managers see counts due by tomorrow in *Needs your attention* on Today (overdue first, each with *Open* and *Edit*), plus due teams with nobody assigned (each with *Assign*); the full schedule stays under Stock → Count → *Scheduled counts*. Overdue counts also reach managers through Shift pulse. Finishing a count completes that team's assignments due by tomorrow, and weekly ones schedule the next date automatically. Someone assigned to another team's count (e.g. a host counting the bar) may count that team. Assignments can be edited or cancelled until done.
- **Par-based suggestions.** Items whose last count is below par and that aren't already on order appear on the order sheet as par minus on hand, rounded up.
- **Receiving.** Arriving POs are checked in line by line. Short quantities and a delivery note are recorded, and what arrived is added to the last count.
- **Vendors.** Contact, account number, delivery days, cut-off time, lead days and minimum order. A vendor with open orders can't be archived.
- **Alerts and reports.** Shift pulse warns managers 8 hours before a cut-off when approved lines are still waiting. It also tells crew when their requests are approved, declined, ordered or received. The Reports hub's **Purchasing** tab shows received spend by vendor, category and team, short-delivery rates, the open pipeline and a consolidated item list. Its CSV includes PO, vendor, category, cost and delivery notes.

**Layout (phone first).** A sticky section bar (Items · Count · 86 · Orders for managers, with Vendors inside Orders; Items · Count · 86 · Requests for crew) replaces the old hero and tile grids. Items is one searchable list with a team picker and status filters (All, 86’d, Below par, On order). Each row shows the name, one status tag and a **+**. Tapping a row opens an item sheet with on hand vs par, vendor and cut-off, open orders, *86 this item*, *Update count* and *Edit item*. Orders show one stage at a time (Review, To order, Arriving, Received). Vendor cards keep the total, cut-off, minimum and *Place order* visible, and fold their lines away on phones. A red banner appears when a cut-off with waiting lines is under three hours away. From 761px rows gain vendor and on-hand columns and cards sit two to a row. From 1100px a summary rail shows what's 86’d now, the next cut-offs and what's waiting on the manager (or the crew member's own requests).

`stock-state.js` owns the catalog, validation and actions (`stock:item`, `stock:vendor`, `stock:count`, `stock:count-start`, `stock:count-entry`, `stock:count-submit`, `stock:count-discard`, `stock:assign`, `stock:assign-cancel`, `stock:request`, `stock:review`, `stock:qty`, `stock:cancel`, `stock:place`, `stock:receive`, `stock:alert`). It also upgrades existing workspaces in place, linking older supply requests and 86 records to stock items by name. `stock-ui.js` renders the screen, which shares the Checklists layout. `stock-demo.js` runs once per fictional workspace (marker `stockDemo`). It adds six months of received deliveries per vendor (including occasional shorts and declined requests) and today's pipeline: crew requests to review, an order sheet across four vendors, two POs arriving, yesterday's short halibut delivery behind tonight's halibut 86, and last night's closing count. It also adds eight weekly counts per team with usage. Floor is left overdue, and a Kitchen count is in progress today. Weekly assignments are added too: Mia's Floor count (overdue since yesterday), a whole-team Kitchen count due today, and Noah's Bar count next week. Costs are estimates from the stock list. There is no supplier integration, invoice matching or automatic sending of orders. Verified by `node scripts/test-stock.mjs`.

Lists are due from the service times (`B.work.due`): opening and set-up lists by the start, mid-shift lists halfway through, closing lists an hour after close; a list still open after its due time shows *Overdue* in the navigator, the list header and Today. The list header shows the station, service, due time and who is on the station; a station's assigned or in-progress stock count appears right above its tasks with *Start count*/*Continue*. Managers toggle *Edit list* (next to the list title) to get edit buttons per task and an inline *Add a task* box (Enter adds and keeps focus; *Tonight only* or *Every [service]*, which also puts it on tonight's list when tonight already has its own list via `alsoShift`), plus *Add several at once*, *Save as the default* and *Clear list*. *Templates* edits service templates in the same layout and *This shift* returns; *History* lists every service in a range with who did what, notes and CSV export (totals and leaderboards are in Reports). Task notes include a *Running low? Request stock* link that opens that station's stock list.

**Stock.** The section tabs (Items · Count · 86 · Orders, or Requests for crew) are an underline bar on wide screens and, on phones, a full-width bar with icons that sticks under the command bar. Every tab count means work waiting there: teams due or mid-count, 86s (reports to review for managers), requests to review, or your open requests. Today, the palette and task notes deep-link into Stock (`stock-go`) with the right tab, order stage and team. Adding an item from its sheet while elsewhere takes you to the request cart. The Count tab drops its KPI tiles (team cards carry items, below-par count and, for managers, on-hand value). Wide screens show an on-hand vs par bar beside each item, and the summary rail lists what is 86'd instead of one large number.

Tests: `test-home.mjs`, `test-reports.mjs`, `test-duties.mjs`, `test-checklist-demo.mjs`, `test-checklist-history.mjs` and `test-stock.mjs` cover the new Today, Checklists and queue markup, list due times and template additions that reach tonight's list.

### Training center

Training is its own tab for every role (sidebar, the More menu on phones, search palette and a card on Today). Manage → Team → Training shows a summary and opens it, the skills matrix stays there, Reports has a Training board, and every HR file and the crew's own file carry a Training section with certificates.

- `assets/js/training-state.js` holds the DOM-free model: `state.training` with courses, assignments, per-person progress, an XP ledger, game scores, daily answers, the sign-off log, ratings, duels and settings. It wraps `Brigly.change`, `starter` and `load` like the other modules and exposes `Brigly.training` (journeys, progress, levels, streaks, badges with progress, certificates, leaderboard, challenges, approver rules, question bank, team overview and the report numbers). Only managers or someone with the **Run training** lead permission can build, publish, assign, nudge or reset; anyone can learn; sign-offs are limited to approvers; course questions are answered by managers, leads and trainers.
- A **course** belongs to a journey stage (Welcome, Core skills, Advanced, Lead) for an audience (Everyone, Managers, a role or a station), can be required, can unlock after another course, and carries objectives, a cover picture, estimated time, XP and a skill it certifies. In order it holds **lessons** (read, watch a video link, look at a picture with a caption, or a *scenario* with graded choices, each with key takeaways), a **quiz** (one question at a time, explanations, a pass mark, unlimited retakes, a review of the misses, every attempt recorded with the questions missed), a **practical** (steps shown on shift, then a sign-off request), **flash cards** and an ordered **routine**. Finishing a course issues a certificate and sets the skill to Trained.
- **Deadlines**: an assignment can carry a due date and note; required courses are automatically due a set number of days after a new hire joins (Settings). Overdue courses show on Today, in notifications, in the overview and in the team view. Managers can nudge someone with a direct message in team chat.
- **Sign-offs**: managers always can; a course can also name trainers of its skill, roles or specific people. Approvers see a queue with the learner's checked steps, note and quiz score, and approve or return with feedback.
- **Gamification**: XP for every lesson, quiz pass, perfect score, practical, course bonus, rating, daily question and duel; five levels with a progress ring; day streaks with a seven-day strip; a personal weekly goal and a team challenge (both in Settings); twelve badges with progress; a leaderboard with a podium, by week, month or all time with a station filter for managers; the **Question of the day** on Training and Today; four games in the Arena (**Speed round**, **Pair up**, **In order**, **True or false**); and **duels**, five shared questions against a teammate with XP for the win. Level-ups, new badges, finished courses and duel wins get a confetti celebration.
- `assets/js/training-ui.js` renders the crew tabs (For you with the journey map, Library, Arena, Sign-offs when relevant) and the manager tabs (Overview, For you, Courses, Team, Arena, Sign-offs, Settings), the course page (objectives, syllabus, practical, reviews, Q&A, certificate, manager tools and stats), the player (outline on desktop, takeaways, quiz review), the transcript per person with CSV export, the course builder (details, lessons, questions, practical and approvers, cards, routine, crew questions, duplicate, reorder, publish) and the Reports board. Actions are `tr-*`; forms use the shared wide dialog with `editing.type === 'training'`.
- Integrations: the Reports **Training** board (completions, XP, active learners, quiz score, pass rate, required training, by-week charts, completion by course, most missed questions, sign-offs, games, duels, the team table and CSV); the HR file and My file **Training** section via `fileSection`; the onboarding checklist step "Required courses finished in Training"; Manage's to-do list and compliance; the Training nav pill and notifications (sign-offs waiting, due or overdue, returned practicals, new courses).
- `scripts/test-training.mjs` covers the seed, the learner flow (lessons, scenarios, quiz pass and fail with misses recorded, prerequisites, sign-off request, approve and return, XP, certificates and the skills matrix), permissions and settings, the course builder, ratings, Q&A, duels, games, the daily question, deadlines and nudges, the report numbers, navigation, notifications and every screen of the UI for both roles.

### My space: the crew's own page

Crew used to have five separate screens (My schedule, Requests, Earnings, My file plus Training). Work and pay now live in one page, **My space**, with a three-way switch (Overview, Earnings, My file). Training stays its own tab, and Today flags any course due before the shift being viewed.

- `assets/js/me-ui.js` renders it. **Overview** is about the person, not the shift (Today already covers the current shift, its briefing and the sick, late and swap actions): the week with a seven-day strip, the shifts in it with who else is on, and week navigation; a "For you" list (write-ups to sign, reviews to read, overdue or returned training, sign-offs waiting, duel challenges); requests inline (swap invitations with accept and decline, open requests with withdraw, recent decisions, a time-off button); a stat strip (pay this month, sick leave, paid time off, training level, each opening its page); and recent kudos. **Earnings** reuses the real pay panel and the schedule-based estimates from `schedule-ui.js` (which exposes `personal`, `requests`, `earnings` and `periodControls`); **My file** comes from `hr-ui.js`.
- Routing: the screen ids stay (`me`, `shifts`, `requests`, `earnings`, `myfile`), so every existing link, notification and Today shortcut still works; `shifts` and `requests` land on the overview. `BriglyNavigation.hub` lists the hub screens, `active()` lights up My space for all of them, the crew dock shows My space instead of Schedule, and the `me` pill carries open requests, then records to read, then overdue training.
- `scripts/test-me.mjs` covers the navigation, the dock, the pill, the overview contents (and that nothing from Today is repeated), Earnings and My file, and that managers keep their screens.
