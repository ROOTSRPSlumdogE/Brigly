# Brigly

The restaurant workspace in `demo.html` has been rebuilt around seven features:

- Team schedules: weekly roster, manager shift creation/editing/removal, overlap checks.
- Opening & closing lists: manager-maintained templates with completion recorded by person for each date and service.
- Specials: service-specific menu notes, prices, ingredient/allergy notes and availability.
- Stock: one stock list per team that drives both the 86 board and purchasing (replaces the separate 86 list and Supplies screens).
- Shift onboarding: lives on Today. Briefings are authored by managers or crew; per-person acknowledgments reset on revisions; shift notes are added, edited and archived in place.
- Reservations: a drawn floor plan with rooms and tables, a live table map with a time scrubber, joined tables, turn times, walk-ins, guest notes and tags, arrival lifecycle, and guest statistics.

## Run locally

Requires Node 20+; no npm dependencies.

```powershell
npm run check
npm run build
npm run preview
```

Open `http://127.0.0.1:8000/demo.html`. The marketing homepage remains in `index.html`.

## Implementation

`assets/js/workspace-state.js` holds the versioned model, validation and mutations. `assets/js/demo.js` renders the seven sections and handles forms. `assets/css/demo.css` provides responsive layouts using Brigly's local Plus Jakarta Sans font and brand palette.

The preview starts with sample data for The Copper Room, seeded for the current local date. Active configured team members are available in the sidebar identity selector, listed with their role title (Server, Bartender, Head chef…); the sidebar profile shows the role and home station. Data is stored under the `brigly-workspace-v2` localStorage key and upgraded in place as features expand; the original nine-module prototype's separate key is preserved but not imported. There is no backend, sign-in, cross-device synchronization, supplier integration or reservation integration. Role controls demonstrate workflows, not security boundaries. Browser storage failures are surfaced in the footer.

Schedules support same-day and overnight assignments. Lists share templates but isolate progress by date and service. Specials, notes, briefings, 86 items and reservations are service-specific; supply requests carry across services. Table bookings use a fixed two-hour window. Allergy notes must be verified with the kitchen.

`npm run check` verifies static references and script syntax, plus state tests for persistence, role controls, scheduling conflicts, shift isolation, briefing revisions, supply approvals and reservation conflicts/lifecycles. `npm run build` writes the static deployment bundle to `dist/`.

## Expanded Team Schedules

The scheduling domain lives in `assets/js/schedule-state.js`; the schedule UI is in `assets/js/schedule-ui.js`. Existing browser data is upgraded in place, preserving all seven modules. Sample hourly rates are seeded for the demo; managers can edit defaults per person or rates and unpaid breaks per shift.

Crew can switch among the sample teammates through **Preview as**, see their weekly shifts and overlapping coworkers, submit time-off requests, report sickness or lateness, request a two-way shift exchange, respond to swap invitations and enter daily tips. Managers see attendance alerts, a review queue, a roster with absence/late markers, individual or whole-team earnings and per-person rate/absence defaults.

Calculation rules:

- Roster hours = shift duration minus unpaid breaks. Expected working hours also remove reported lateness and absences.
- Time off changes estimates only when approved. Managers can choose paid/unpaid for each request, including correcting approved leave.
- Sickness updates expected coverage immediately, using the person's saved paid/unpaid default provisionally; manager review can override it. No medical details are required.
- Lateness updates expected minutes immediately. A manager can confirm or correct the minutes, including zero. Sickness takes precedence over lateness to avoid double deductions.
- Gross wages = (expected working hours + paid absence hours) × the saved shift rate, rounded to cents per shift. Reported daily tips are added to the total. Editing a tip entry replaces that person's total for that date.
- Daily, Monday–Sunday weekly, calendar-month and overall summaries use the selected date and include all services. Past values remain estimates, not verified worked time. There is no tax, overtime, deductions or payroll processing.
- Default rate changes affect new shifts only. Existing shifts retain their rates. Absence default changes affect new requests only.
- Swaps require the invited teammate's acceptance and then manager approval. Both assignments exchange atomically; each person retains their prior rate for the exchange. Conflicts, approved leave and attendance are rechecked. Editing a referenced shift invalidates a pending swap.
- Browser tabs on the same origin receive updates. An open form becomes stale if another tab changes the workspace and must be reopened before saving. This is still a local prototype; it does not send external notifications or synchronize between devices.

Verification covers state migration, paid/unpaid overrides, absence and lateness calculations, tip replacement, period aggregation, actor restrictions, teammate consent, swap approval/conflicts, stale swaps and default rates. Browser checks cover the crew/manager workflows, persistence, tab updates, stale forms and desktop/mobile layouts.

## Floor plan, live table map and guest statistics

`assets/js/floor-state.js` holds the floor plan and everything the reservations screen asks about tables and guests; `assets/js/floor-ui.js` renders the Reservations screen and the guest section of the Guests & reservations report. Existing workspaces are upgraded in place: every booking keeps its table text, which becomes a list of table labels, and any label not on the plan gets a table so no booking loses its place.

- **Reservations screen.** Two views: **Floor plan** and **Bookings**, with **Walk-in** and **Booking** as the only primary actions. The floor view shows a strip of live numbers, a time control (live, replay or preview with a covers-per-half-hour trace), one room at a time with room chips, and the service’s bookings beside the map grouped into *Needs attention* (late or without a table), *Arriving* and *Seated*, each with one quick action. Tapping a table opens its sheet (seat, complete, walk-in, book, move a waiting party here); tapping a booking opens its sheet (seat, pick or move table, edit, guest profile, no-show, cancel).
- **Tap to assign.** “Pick table” or “Move table” puts the map into pick mode: fitting tables are outlined, busy or too-small ones fade, tapping toggles a table and a second tap on another table joins them; the banner confirms with *Seat here*, *Assign only* or *Move here*. Escape cancels.
- **Rooms and tables.** The plan is a set of rooms (sections), each a grid of cells, with tables placed by cell position and size. A table has a short unique label (what bookings use), standard seats, a maximum capacity and a shape (round, square, rectangle, booth, high-top). The map scales cells to the available width, down to a minimum so labels stay readable, and scrolls sideways beyond that.
- **Layout editor** (managers, or crew with the “Edit the floor plan” lead permission) is a focused mode behind *Edit layout*: add tables from shape presets, drag them into place, drag the corner to resize, nudge with arrow keys (Shift resizes), and set label, seats, capacity, shape and room in the side panel (a bottom sheet on phones). Rooms can be added, renamed, resized, reordered and removed when empty. Tables cannot overlap or leave the room; labels must be unique across the plan; renaming a label follows every booking that uses it; removing a table frees it from upcoming bookings but keeps history.
- **Bookings.** A booking can hold up to four tables, a turn time (30 minutes to 6 hours; the default is set in the editor), a source, tags and a contact. Conflicts are checked per table on the booking’s date using real turn windows, and a party cannot be booked onto tables whose combined maximum is too small. The form suggests free single tables or neighbouring pairs for the chosen time, with every table’s fit and availability one tap away; contact, tags and notes sit behind a disclosure so the common case stays short. Seating, completing and closing a booking stamp the time.
- **Walk-ins.** Seat a party straight onto a free table; the turn is shortened automatically when the table is booked later and refused when fewer than 45 minutes remain.
- **Guest statistics** live in **Reports › Guests & reservations**: returning versus new guests, regulars (4+ visits), visit-frequency cohorts, booking sources, tags, seat utilization per room, most booked tables, guests to watch (repeat no-shows) and a searchable guest directory ranked by visits in the period. A guest profile (also reachable from any booking) lists visits, covers, no-shows, reliability, usual time, favourite table and room, time at the table, notes from past bookings and the visit history, and can start a new booking with the guest’s details prefilled.

The plan lives under `state.floor`; `npm run check` runs `scripts/test-floor.mjs`, which covers migration, legacy free-text tables, conflict and capacity rules, lifecycle stamps, walk-ins, permissions, the editor rules, occupancy, suggestions, pacing, guest statistics, tap-to-assign and the rendered views.

## Shared shift operations and manager reporting

`shift-operations-state.js` and `shift-operations-ui.js` connect the schedule with notes, menu availability, reservations, team configuration and reports.

- A shared shift is a **service date + service name**. Notes appear in each matching crew shift card and in Onboarding. Manager-authored notes are highlighted and sorted first; crew can edit/archive their own notes. Crew need an assignment on that service to post.
- The 86 list is now service-specific. Crew submissions are **Reported** (unconfirmed); managers approve or decline with feedback. Manager-created items start **Approved**. Managers can mark stock available again. Earlier global 86 data migrates to its saved date/service. Pending reports are available across dates in the manager's **86 review** tab.
- Shift briefings display reservation arrivals, parties, tables, guest notes and status; the linked reservation editor retains the selected date/service.
- **Team & schedule setup** supports adding/editing/archiving people, role titles, default stations and manager/crew access. Archiving preserves history and prevents new assignments. Role and station names can be added/renamed; only unused options can be removed.
- Services can be added, renamed or archived, with default start/end times and unpaid breaks. Renaming preserves linked notes, reservations, 86 items and checklist progress. Time changes apply to new assignments by default; managers may explicitly update assignments from a chosen date. Conflicts block the entire change. Individual assignments remain editable.
- Overnight shifts are supported. An end time before its start finishes the following day. Reports attribute the whole assignment to its service/start date. Overlap checks span midnight.
- Manager dashboards show **estimated labor cost**, using gross wages including paid absence, excluding crew tips. Crew dashboards retain **expected gross earnings** including their tips. Employer taxes/benefits, overtime, clocked actual hours and payroll finalization are not modeled.
- **Team reports** generates live statistics for a chosen person and date range: shifts, roster/expected hours, paid/unpaid absence hours, sickness/time-off counts, reported and confirmed late shifts, late minutes, pending reviews, wage expense, separate tips, note/86 contributions and per-shift records. “Not recorded” is distinct from on-time attendance. There are no inferred performance scores or automated employment recommendations.
- CSV downloads contain the same person/date scope and per-shift data, with formula-safe text cells. Reports are recalculated in the app; no emails, external HR integrations or scheduled background jobs are sent or created.

The preview identity selector now includes all active configured team members. Manager access is a simulated application role; this browser-local prototype still requires a backend and real authorization before shared production use.

### Stock: the stock list, 86 board and purchasing in one place

The separate 86 board and Supplies screens are combined into **Stock** (sidebar, phone dock and service rail). Old `#eighty-six`, `#orders` and `#supply` links, saved views and notifications open the matching Stock section.

- **Stock list.** Managers keep one catalog of items. Each item has a category, vendor (or *Made in house*), the **teams** (stations) that may use it, order unit and pack size, unit cost, par level, storage area and an optional vendor SKU. Crew see only items for their teams: their home station plus any station they are rostered on for the selected service. A bartender can 86 or order limes but not halibut; kitchen crew can. Other teams' lists are view-only. Rows show live status: 86’d this service, below par, requested, on the order sheet, on order with its arrival date.
- **86 from the list.** The 86 action and every older entry point (Today, shift sheets) open a picker limited to the team's items. It offers quick reasons and an optional restock request in the same step. Crew 86s stay *Reported* until a manager approves them, as before. An item can't be 86’d twice for one service. Free-text 86s from checklist notes link to stock items when the name matches. On the 86 board, each card shows whether a restock is requested, on the order sheet, or arriving.
- **Ordering.** Crew tap **+** to build a request (cart) and send it with a note. Managers review requests: adjust quantities, approve, or decline with a reason. Manager additions skip review, and repeat additions merge into one line.
- **Order sheet (manager).** Approved lines are grouped **by vendor** (default, one purchase order per vendor), **by team** or **by category**. Vendor cards are sorted by the next order cut-off. Each shows delivery days, the cut-off and arrival date, an estimated total and progress toward the vendor minimum. **Copy order** gives formatted text or CSV for emailing the rep. **Place order** assigns a PO number and the expected delivery date.
- **Inventory counts (Count).** Crew count their own teams; managers can count any team. Each team has one open count sheet at a time. The sheet is grouped by storage area in walking order (walk-in, freezer, pastry, dry store, bar back, beer cooler, wine cellar, front of house, supply closet), shelf to sheet. Each row has a −/number/+ control and a *Last count* shortcut, Enter moves to the next item, and entries save as you go, so several teammates can count together or pick it up later. Finishing updates on-hand for counted items; skipped items keep their last count. It also records **usage** per item: last count + deliveries checked in − this count. A negative usage ("more than expected") points to a delivery that wasn't checked in, or a miscount. A result card then offers to request or order everything that came out below par. Teams are **due** after 7 days without a finished count. Due and in-progress counts appear on the Count tab badge, in Shift pulse and in the summary rail. Managers also see on-hand value (quantity × unit cost) per team. Count history opens each count with per-item usage. *Update count* in the item sheet stays for quick spot checks.
- **Count assignments.** Managers assign a count from Stock → Count (*Assign* on a team card or under *Scheduled counts*) or from Today. Each assignment has a team, a person or the whole team, a due date, an optional note and an optional weekly repeat. The counter sees it on **Today** in *Up next for you* from the day before (due date, note, progress) with *Start count* / *Continue*, which opens the count sheet directly. It also appears on their team card in Stock → Count, at the top of that team's list in Checklists, and Shift pulse reminds them the day before, on the day and once it's overdue. Managers see counts due by tomorrow in *Needs your attention* on Today (overdue first, each with *Open* and *Edit*), plus due teams with nobody assigned (each with *Assign*); the full schedule stays under Stock → Count → *Scheduled counts*. Overdue counts also reach managers through Shift pulse. Finishing a count completes that team's assignments due by tomorrow, and weekly ones schedule the next date automatically. Someone assigned to another team's count (e.g. a host counting the bar) may count that team. Assignments can be edited or cancelled until done.
- **Par-based suggestions.** Items whose last count is below par and that aren't already on order appear on the order sheet as par minus on hand, rounded up.
- **Receiving.** Arriving POs are checked in line by line. Short quantities and a delivery note are recorded, and what arrived is added to the last count.
- **Vendors.** Contact, account number, delivery days, cut-off time, lead days and minimum order. A vendor with open orders can't be archived.
- **Alerts and reports.** Shift pulse warns managers 8 hours before a cut-off when approved lines are still waiting. It also tells crew when their requests are approved, declined, ordered or received. The Reports hub's **Purchasing** tab shows received spend by vendor, category and team, short-delivery rates, the open pipeline and a consolidated item list. Its CSV includes PO, vendor, category, cost and delivery notes.

**Layout (phone first).** A sticky section bar (Items · Count · 86 · Orders for managers, with Vendors inside Orders; Items · Count · 86 · Requests for crew) replaces the old hero and tile grids. Items is one searchable list with a team picker and status filters (All, 86’d, Below par, On order). Each row shows the name, one status tag and a **+**. Tapping a row opens an item sheet with on hand vs par, vendor and cut-off, open orders, *86 this item*, *Update count* and *Edit item*. Orders show one stage at a time (Review, To order, Arriving, Received). Vendor cards keep the total, cut-off, minimum and *Place order* visible, and fold their lines away on phones. A red banner appears when a cut-off with waiting lines is under three hours away. From 761px rows gain vendor and on-hand columns and cards sit two to a row. From 1100px a summary rail shows what's 86’d now, the next cut-offs and what's waiting on the manager (or the crew member's own requests).

`stock-state.js` owns the catalog, validation and actions (`stock:item`, `stock:vendor`, `stock:count`, `stock:count-start`, `stock:count-entry`, `stock:count-submit`, `stock:count-discard`, `stock:assign`, `stock:assign-cancel`, `stock:request`, `stock:review`, `stock:qty`, `stock:cancel`, `stock:place`, `stock:receive`, `stock:alert`). It also upgrades existing workspaces in place, linking older supply requests and 86 records to stock items by name. `stock-ui.js` renders the screen, which shares the Checklists layout. `stock-demo.js` runs once per fictional workspace (marker `stockDemo`). It adds six months of received deliveries per vendor (including occasional shorts and declined requests) and today's pipeline: crew requests to review, an order sheet across four vendors, two POs arriving, yesterday's short halibut delivery behind tonight's halibut 86, and last night's closing count. It also adds eight weekly counts per team with usage. Floor is left overdue, and a Kitchen count is in progress today. Weekly assignments are added too: Mia's Floor count (overdue since yesterday), a whole-team Kitchen count due today, and Noah's Bar count next week. Costs are estimates from the stock list. There is no supplier integration, invoice matching or automatic sending of orders. Verified by `node scripts/test-stock.mjs`.

### Command bar, Today and connected service screens

**Undo.** Ticking or reopening a checklist task (on Today or Checklists) shows a toast with *Undo* for six seconds.

**Today.** One board for the selected shift, without statistics (trends and totals live in Reports):

- *Shift card*: live/upcoming/ended state, times, station, hours and estimated wages (crew) or people on shift, guests booked and 86 count (managers), status (on shift, late, absent, full team, people out), a progress bar with time in and time left while live, and who you are working with (tap to jump to the team list). Crew who aren't on the selected service see their other shift that day or their next one, with a button to switch.
- *Quick actions*: eight one-tap actions (crew: report 86, request stock, add note, tips, running late, sick, swap, time off; managers: briefing, note, 86, order stock, assign count, add shift, roster, inbox).
- *Needs your attention* (managers) / *Up next for you* (crew): one prioritised list with inline actions. Managers: people out (find cover), late arrivals, missing briefing (post), 86 reports (approve/decline), vendor cut-offs within 8 hours (place order), crew stock requests (approve all/review), deliveries due or overdue (check in), counts due by tomorrow or overdue, due teams nobody is assigned to (assign), items below par not on order, pending schedule requests, lists still open after they were due. Crew: swap invitations, their stock counts, unfinished lists on their station, priority-flagged tasks, their 86 reports awaiting a manager, request updates (declined/ordered/arrived) and chat to-dos for them (Done/Open). Five show at once; the rest fold under *Show more*.
- *Checklist*: crew tick off their station's next tasks in place (tonight-only tasks pinned on top, priority notes first), switch lists with tabs that show progress and due time, and see when a finished list was completed and by whom. Managers get one row per station with progress, the next open task, late lists and priority flags; each row opens that station's list.
- *Briefing*: unread briefings sit at the top for crew with *I've read it*; read ones and the manager view sit lower. Long briefings fold behind *Read more*. Managers and authors see who has read it, can send a one-tap *Remind* to the team chat naming who hasn't, and can edit. An author counts as having read their own briefing (the Today badge and alerts follow).
- *Before taking orders* (86s with restock status from Stock: arriving date, on the order sheet or requested; *Back in stock* for managers; tap an item to open its stock sheet), *Specials*, *Arrivals* (seat/complete), *On shift* (status only when it matters, unread briefings for managers, tap to message), *Shift notes* and *Team chat*.
- Wide screens show a main column and a board rail; tablets stack the rail in two columns; phones show one column ordered shift → actions → unread briefing → queue → checklist → 86 → specials → briefing → arrivals → team → notes → chat.

**Checklists.** Crew only see their checklist: the station navigator (wide screens) or the station bar and list pills (phones) and the list itself. Managers also get a tab bar across the top, the same as Stock’s: *Shift lists* (badge = lists running late), *Templates*, *History* and *New list*; it is an underline row on wide screens and icon tabs on phones, where the station bar below it sticks under the command bar as you scroll. Templates shows a green banner with the service chips above the same layout. Wide screens show the navigator (every station with its lists, each with progress and due time) beside the selected list; phones and tablets show stations as icon tabs (badge = tasks still open, a check when done, a dot on your own station) with the lists as pills beneath. Lists are due from the service times (`B.work.due`): opening and set-up lists by the start, mid-shift lists halfway through, closing lists an hour after close; a list still open after its due time shows *Overdue* in the navigator, the list header and Today. The list header shows the station, service, due time and who is on the station; a station's assigned or in-progress stock count appears right above its tasks with *Start count*/*Continue*. Managers toggle *Edit list* (next to the list title) to get edit buttons per task and an inline *Add a task* box (Enter adds and keeps focus; *Tonight only* or *Every [service]*, which also puts it on tonight's list when tonight already has its own list via `alsoShift`), plus *Add several at once*, *Save as the default* and *Clear list*. *Templates* edits service templates in the same layout and *This shift* returns; *History* lists every service in a range with who did what, notes and CSV export (totals and leaderboards are in Reports). Task notes include a *Running low? Request stock* link that opens that station's stock list.

**Stock.** The section tabs (Items · Count · 86 · Orders, or Requests for crew) are an underline bar on wide screens and, on phones, a full-width bar with icons that sticks under the command bar. Every tab count means work waiting there: teams due or mid-count, 86s (reports to review for managers), requests to review, or your open requests. Today, the palette and task notes deep-link into Stock (`stock-go`) with the right tab, order stage and team. Adding an item from its sheet while elsewhere takes you to the request cart. The Count tab drops its KPI tiles (team cards carry items, below-par count and, for managers, on-hand value). Wide screens show an on-hand vs par bar beside each item, and the summary rail lists what is 86'd instead of one large number.

### Training center

Training is its own tab for every role (sidebar, the More menu on phones, search palette and a card on Today). Manage → Team → Training shows a summary and opens it, the skills matrix stays there, Reports has a Training board, and every HR file and the crew's own file carry a Training section with certificates.

- `assets/js/training-state.js` holds the DOM-free model: `state.training` with courses, assignments, per-person progress, an XP ledger, game scores, daily answers, the sign-off log, ratings, duels and settings. It wraps `Brigly.change`, `starter` and `load` like the other modules and exposes `Brigly.training` (journeys, progress, levels, streaks, badges with progress, certificates, leaderboard, challenges, approver rules, question bank, team overview and the report numbers). Only managers or someone with the **Run training** lead permission can build, publish, assign, nudge or reset; anyone can learn; sign-offs are limited to approvers; course questions are answered by managers, leads and trainers.
- A **course** belongs to a journey stage (Welcome, Core skills, Advanced, Lead) for an audience (Everyone, Managers, a role or a station), can be required, can unlock after another course, and carries objectives, a cover picture, estimated time, XP and a skill it certifies. In order it holds **lessons** (read, watch a video link, look at a picture with a caption, or a *scenario* with graded choices, each with key takeaways), a **quiz** (one question at a time, explanations, a pass mark, unlimited retakes, a review of the misses, every attempt recorded with the questions missed), a **practical** (steps shown on shift, then a sign-off request), **flash cards** and an ordered **routine**. Finishing a course issues a certificate and sets the skill to Trained.
- **Deadlines**: an assignment can carry a due date and note; required courses are automatically due a set number of days after a new hire joins (Settings). Overdue courses show on Today, in notifications, in the overview and in the team view. Managers can nudge someone with a direct message in team chat.
- **Sign-offs**: managers always can; a course can also name trainers of its skill, roles or specific people. Approvers see a queue with the learner's checked steps, note and quiz score, and approve or return with feedback.
- **Gamification**: XP for every lesson, quiz pass, perfect score, practical, course bonus, rating, daily question and duel; five levels with a progress ring; day streaks with a seven-day strip; a personal weekly goal and a team challenge (both in Settings); twelve badges with progress; a leaderboard with a podium, by week, month or all time with a station filter for managers; the **Question of the day** on Training and Today; four games in the Arena (**Speed round**, **Pair up**, **In order**, **True or false**); and **duels**, five shared questions against a teammate with XP for the win. Level-ups, new badges, finished courses and duel wins get a confetti celebration.
- `assets/js/training-ui.js` renders the crew tabs (For you with the journey map, Library, Arena, Sign-offs when relevant) and the manager tabs (Overview, For you, Courses, Team, Arena, Sign-offs, Settings), the course page (objectives, syllabus, practical, reviews, Q&A, certificate, manager tools and stats), the player (outline on desktop, takeaways, quiz review), the transcript per person with CSV export, the course builder (details, lessons, questions, practical and approvers, cards, routine, crew questions, duplicate, reorder, publish) and the Reports board. Actions are `tr-*`; forms use the shared wide dialog with `editing.type === 'training'`.
- Integrations: the Reports **Training** board (completions, XP, active learners, quiz score, pass rate, required training, by-week charts, completion by course, most missed questions, sign-offs, games, duels, the team table and CSV); the HR file and My file **Training** section via `fileSection`; the onboarding checklist step "Required courses finished in Training"; Manage's to-do list and compliance; the Training nav pill and notifications (sign-offs waiting, due or overdue, returned practicals, new courses).

### Menu: dishes, recipes, allergens and availability

**Menu** is its own screen in Live service (sidebar, service rail, More and the palette). It follows the shift in the command bar, because availability does.

- **Menu tab.** A stats strip fed by the POS (dishes on, off now, counts running, happy hour now or next, four-week food cost for leads), a category rail (sticky on desktop, chips on a phone) whose colours are the same ones the POS tiles use, search by name, description, allergen, diet or tag, sort (menu order, A–Z, price, and for leads food cost or best sellers) and a cards/list toggle. Each card shows the price (with the happy-hour price struck through while it runs), allergen codes, dietary shorthand (V, VG, GF…), and a live availability tag: *86’d*, *Out · ingredient* when an ingredient on the stock list is 86’d, *Sold out* and *n left* from the kitchen’s count, *Not at Dinner* for day-part categories, *Low* when an ingredient is below par and not on order. Leads also see the food-cost percentage and four-week sales. The dish sheet holds the description, allergens (derived from the recipe plus the kitchen’s own flags and “may contain” notes), the recipe with each ingredient’s stock status and portion cost, cost, margin and price, prep and plating notes, modifiers, and an **At the till** panel straight from the POS: what it rings in at (happy-hour price and window), the tax rate and group, sold today and how many open checks carry it (and how many are not sent yet), the count for the service, and its four-week sales with its menu-engineering class. Actions: 86 (crew report or manager 86, landing on the shared 86 board with the dish linked), back on, set or change a count, change the price, edit, duplicate, move up or down (the POS tiles follow), archive.
- **Allergens tab.** Tap what a guest avoids and the finder lists every dish safe for them, by course; below it the full matrix of dishes × fourteen allergens (● contains, ○ may contain). Ingredient allergens are kept per stock item in Setup, so a change to one ingredient updates every dish that uses it.
- **86 & counts tab.** What is off right now and why: dishes 86’d (with how many open checks still carry them), dishes off because an ingredient is 86’d (with a link to the stock item), dishes sold out by count, crew reports waiting for a manager, the **counts for the service** (the kitchen sets how many portions there are; the POS counts each one down, shows *n left* on the tile, refuses the dish at zero and marks it sold out), dishes running low, and a fold for dishes in day-part categories not served at this service.
- **Performance tab (leads).** Menu engineering from POS sales for today, 7 days, 28 days or 12 weeks: units, net, food cost against the target, margin per unit; the four quadrants (Stars, Plow horses, Puzzles, Dogs, each classed against the other dishes in its own category so a soda is never a dog next to the rib-eye) with the dishes in each; every dish ranked with sold, mix, net, cost %, margin and class; and the dishes with no sales in the period.
- **Setup (managers, or crew with the “Run the menu” lead permission).** Categories (course, station, order, colour, the services they are sold at so a Brunch category only shows on the POS at lunch, and a note of their POS tax group and happy-hour status), modifier groups (required or optional, pick one or several, option prices), ingredient allergens (searchable) and the target food cost. The dish form builds the recipe from the stock list: a portion label for people (180 g) and the order units one portion uses (0.18 of a kilo), which drives cost and allergens.

`assets/js/menu-state.js` holds `state.menu` and the actions (`menu:item`, `menu:archive`, `menu:category`, `menu:category-order`, `menu:remove-category`, `menu:modifier`, `menu:remove-modifier`, `menu:ingredient`, `menu:settings`, `menu:86`, `menu:limit` (the count for a service, by leads or anyone who can report 86s), `menu:price`, `menu:duplicate`, `menu:item-order`) plus the derived helpers in `Brigly.menu` (allergens, cost and margin, availability, the allergen finder and matrix, outs including counts and day-parts, sold and remaining for a service, which open checks carry a dish, the category colour shared with the POS, which dishes use a stock item). Station renames follow; a station in use can’t be removed. `assets/js/menu-ui.js` renders the screen with the Stock layout. The starter menu for The Copper Room has 46 dishes and drinks built on the stock catalog. Verified by `node scripts/test-menu.mjs`.

### POS: floor, orders, kitchen, cash, close-out and sales

**POS** is the till for the shift in the command bar, built to the feature set of the full-service systems restaurants run today (Toast, Square for Restaurants, Lightspeed, TouchBistro) on Brigly’s own records: tables come from the floor plan, dishes, prices, modifiers and 86s from Menu and Stock, happy hours from Happenings, servers and labor from the roster, and tips, sales and cash flow into earnings, the daily close and Reports. The layout follows the systems servers already know (Square, Toast): one header row with the tabs, a chip for who is on the till (tap for PIN switch, clock in/out, the drawer and your PIN) and *New check* with the other order types behind it; a floor map beside a quiet rail; the sidebar folds to an icon rail while the POS is open so the till has the whole screen; and an order screen built around the table: the check on the left, the menu in the middle and a rail of check actions on the right, with one Send / Pay bar.

- **Floor.** The floor plan with each table’s server initials (its section) and any open check: the total, how long it has been open and where the order stands (ordering, in the kitchen, ready, served, check dropped, paying), an allergy marker where a check carries one, and the count when a table has several checks. A strip shows open checks, money on the floor, net so far, covers paid, pickups due and late tickets. Beside the map, three lanes: tables, bar tabs, and the takeout and delivery queue sorted by pickup time with overdue orders flagged. Tapping a table opens its check (or a picker when there are several) or starts one. Opening a check on a free table seats a walk-in, so the live table map in Reservations shows the party; a table with a seated booking links to it, and paying the last check completes the visit and frees the table.
- **Order types.** Dine-in, bar tab (optionally with a card on file and a pre-authorised amount), takeout and delivery (name, phone and a pickup time defaulted from the prep time in settings; online orders are tagged). Each type can be turned off in settings. A tab that takes a table becomes dine-in; takeout never holds courses.
- **Order screen.** The menu beside the check: search, category tabs with *Top sellers* (last four weeks) and *Open item & gift cards*, tiles tinted by category (allergens in the tooltip and on the item sheet), 86’d and sold-out dishes greyed out, *n left* while a kitchen count runs (the POS refuses the item past the count), day-part categories hidden outside their service, low-stock and happy-hour flags with the struck list price. Items with options open a sheet for required and optional modifiers, quantity, seat, course and a note with quick phrases. The check groups lines by course under *To send* and *Sent*, with seats, modifiers, notes, promos and discounts on each line, a stepper on held lines and a coloured dot for where a sent line stands. Tapping items selects them and a bar offers everything you can do with the selection: move to a new or another check, **share the cost** between guests (equal shares, one per seat), change seat and course, edit, discount, comp, void or remove. **Coursing:** *Send* fires drinks and the first food course and holds later courses on the pass (“Holding”); the server or the expo fires the next course from the check or the kitchen display. *Drop check* marks the check presented. *Repeat round* rings the last round of drinks again. The rail holds the check-level actions: *Table* (the table sheet: party, booking, server and section, time seated, totals, a timeline from opened to paid, other checks on the table, and action tiles), *Details* (guests, name, phone, pickup time, allergy note, order type, card on file, service charge), split, merge, move table or server, repeat round, discount, drop check, receipt, void, reopen and refund. The table name in the header opens the same sheet. *Split* by seat (shared items spread across the seats), evenly into n checks (each line becomes a 1/n share) or by item (tick lines, move them to a new or another open check); *Merge* folds another check in; *Transfer* moves the check to another server or table (joining a table that already has one). Leads void sent items, comp items, discount an item or the whole check (presets such as Staff meal and Industry, or percent/amount with a reason), void checks and reopen paid ones. The receipt itemises by seat, shows tip suggestions on an open check, and can be copied, “printed” or “emailed” (simulated).
- **Payments.** Tender buttons, a numpad, *Pay it all* / *Split by n*, tip suggestions, cash tendered with quick $20/$50/$100 and the change due, gift card codes with the live balance, and house accounts with their limit. Several payments can land on one check; the pre-auth is shown against the due amount on a tab. After a check is paid, the server or a lead can **adjust a card tip** from the signed slip the same day, and a lead can **refund** part or all of what was paid (by any tender, with a reason). Totals follow the settings: a default tax rate plus a second tax group by menu category (alcohol by default), tax-inclusive pricing if wanted, rounding of the total, the automatic service charge from the party size.
- **Tickets.** The kitchen and bar display: expo (every station) or one station, oldest first, a green/amber/red bar and timer by ticket age against the thresholds in settings, courses inside each ticket, the allergy note on top, takeout and delivery tickets marked with their pickup time, held courses shown with a *Fire* button; tapping a line moves it along (cooking → on the pass → served), *All ready* and *Bump all* per ticket. *All day* adds up everything on the rail by item; *Recent* lists what was bumped in the last twenty minutes with *Recall*.
- **Cash.** The drawer for the service: open it with a float, see the expected cash (float + cash sales − cash refunds + paid in − paid out − drops), record *Paid in*, *Paid out* (over 50 needs a lead), *Cash drop* and *No sale*, then *Count & close* with an optional count by denomination and the over/short shown live. Closed drawers list expected against counted; leads can reopen one. **Gift cards** are sold from the order screen (any amount; the code activates when the check is paid), redeemed as a tender, looked up by code and topped up by a manager. **House accounts** carry a balance and a limit, are charged as a tender and settled from the Cash tab (a cash settlement lands in the open drawer).
- **Close-out.** Each server’s sheet for the shift or the day: net sales, checks and covers, tips (card, cash and service charge), cash to hand in after cash tips, card tips owed, the suggested tip-out by station and tips after tip-out, plus refunds. Managers see the service’s KPIs (net, average check, tips, **labor** cost and sales per labor hour from the roster, comps/discounts/voids/refunds, the drawer result, open checks), every server, the payment mix, sales by order type, every adjustment with its reason and name, and the **journal**: every void, comp, discount, refund, tip change, drawer entry, split, merge, reopen, gift card and account movement for the day, filterable by kind. Buttons for the daily close, the **Z report** (an end-of-day text report to copy or print), *Archive the day’s checks*, POS settings and PINs.
- **Settings (managers).** Taxes and rounding (default rate, second tax group and its categories, tax-inclusive prices), service charge and party size, tip suggestions, default float, tenders, tip-out, order types, coursing on or off, takeout prep time, ticket amber and late thresholds, stock depletion, how many days of full checks to keep, discount presets, happy-hour pricing (percentage and categories; it applies while a happy-hour happening with a time window is live), receipt header and footer, void and comp reasons.
- **Training mode.** Leads open a *Training check* that rings, sends and pays like any other but never counts in sales, tips, stock or the drawer.
- **Everywhere else.** Today shows *Sales* (managers, with pickups and the drawer state), *My tables* (servers) or *Kitchen/Bar tickets* (crew on those stations). Reservations’ live map shows server initials and open checks and offers *Open check* on a table. Paying a check takes the recipe ingredients of each dish off counted stock. The daily close starts from the POS net per service and can take the drawer’s over/short. Reports’ **POS & servers** board gains labor %, cash over/short, refunds, happy-hour promotions and sales by order type beside servers, hours, tenders, categories and the menu mix. The palette finds open checks and dishes; the POS pill counts open checks and late tickets.
- **Permissions.** *Use the POS* is an everyday permission (on by default): open checks, ring, send, fire, bump, pay, open and count the drawer. *Run the POS* (lead): void sent items, comps, discounts, refunds, tip adjustments on others’ checks, other servers’ checks, sections, transfers, training checks, open items, house accounts, drawer reopen and POS settings (managers for settings, gift card balances and other people’s PINs).

`assets/js/pos-state.js` holds `state.pos` (version 2): settings, checks (with order type, lines carrying their tax rate, promo, item discount or split share, payments, refunds), sections per service, compact day rollups (now with order types, promos, refunds, gift cards and the drawer count), drawers, gift cards, house accounts, the journal (capped at 300 entries) and PINs. Actions: `pos:open` (`type_`, `pickupAt`, `phone`, `allergy`, `card`/`preauth`, `training`), `pos:add` (menu items, `open-item`, `gift-card`), `pos:repeat`, `pos:line`, `pos:remove-line`, `pos:send`, `pos:fire`, `pos:bump` (one line or several), `pos:void-line`, `pos:comp`, `pos:discount` (check or `line`, `preset`), `pos:remove-discount`, `pos:update`, `pos:present`, `pos:transfer`, `pos:move-lines`, `pos:split-line` (share one item between n guests), `pos:split` (`seats` or `even`), `pos:merge`, `pos:pay`, `pos:remove-payment`, `pos:tip`, `pos:refund`, `pos:close`, `pos:reopen`, `pos:void`, `pos:section`, `pos:section-table`, `pos:section-auto`, `pos:section-clear`, `pos:drawer-open`, `pos:drawer-event` (`in`, `out`, `drop`, `nosale`), `pos:drawer-close`, `pos:drawer-reopen`, `pos:gift-adjust`, `pos:account`, `pos:account-settle`, `pos:pin`, `pos:settings`, `pos:consolidate`. `Brigly.pos` exposes totals, table state (with every check on the table), tickets (with held courses), all-day counts, recent bumps, the drawer and its expected cash, gift cards and accounts, happy-hour pricing, labor, sales over a period, the server report, menu engineering, tips, PINs and the Z report. A version-1 record upgrades in place. Paying a check writes the server’s POS tips for that date into `scheduling.tips` (`source: 'pos'`). `assets/js/pos-ui.js` renders the command bar, floor, orders and order screen with its dialogs; `assets/js/pos-views.js` renders the kitchen display, cash, close-out, sections, settings, the Today card and the Reports board. `assets/js/pos-demo.js` seeds the fictional workspace once with twelve weeks of day rollups that add up to the recorded sales (dine-in, tabs, takeout and delivery), two days of full checks with closed drawers and their counts, gift cards, house accounts and a journal, sections for the coming services and a live service today (parties seated with checks in progress, courses holding, bar tabs with a card on file, takeout due, the drawer open), then keeps today fresh and folds older days into rollups so the workspace stays inside browser storage. Tax, service charge, tip-out and labor are configurable estimates; the card terminal, printer, cash drawer hardware, payment processor, email and online-ordering feeds are simulated.
